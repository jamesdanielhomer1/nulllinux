# Moving this disk to another machine

Written 2026-09-03, for the disk in `nox`. Everything below was checked on the
machine, not assumed.

## It will boot

| | |
|---|---|
| Firmware | UEFI. `/boot/efi/EFI/BOOT/BOOTX64.EFI` is shim, so a new board finds it with no NVRAM entry, and Secure Boot may be left on. |
| Initramfs | **Generic**, not host-only — see below. |
| `/etc/fstab` | Every entry is a UUID. Nothing names a device node. |
| Swap | zram. No swap partition to find. |
| Root | btrfs, and btrfs + ext4 are built into the kernel. |
| Graphics | nouveau and i915 only, no proprietary driver; full `linux-firmware`, so amdgpu/radeon/nvidia firmware is already on disk. |
| Units | Nothing is bound to a device. No failed units. |

### The one thing that had to change

Fedora builds a **host-only** initramfs: drivers for the storage this machine
has, and nothing else. On this disk that was `nvme`, `virtio_scsi` and `vmd`.
Moved to a machine that reaches its root over USB, or a RAID controller, it
would have dropped to a dracut emergency shell — unable to see its own root.

`/etc/dracut.conf.d/99-portable.conf` now sets `hostonly="no"`. It has to be a
config file rather than a one-off `dracut --no-hostonly`, because every kernel
update rebuilds the initramfs and would silently undo a one-off.

Cost: 153 MB → 236 MB per image, out of 2 GB of `/boot` with 1.3 GB free.

Reachable root paths afterwards, verified against the built image:

    NVMe M.2          nvme.ko + nvme-core.ko
    SATA / AHCI       ahci, sd_mod        (built into the kernel)
    USB enclosure     xhci-pci builtin, usb-storage.ko + uas.ko
    SD / eMMC         sdhci-pci.ko
    RAID / SAS HBA    83 scsi and ata drivers
    virtio (a VM)     virtio_pci builtin + virtio_scsi.ko

### What would still stop it

- **A BIOS-only machine.** This disk is UEFI only: no BIOS boot partition and
  no MBR bootloader. There is 0.98 MiB of free space at the front of the disk
  and a BIOS boot partition needs 1 MiB, so it cannot be added without
  repartitioning.

## The desktop

The bar and the column now ask the compositor how big the screen is instead of
assuming 1920x1080, so they fill any resolution. Verified at 1280x720,
1600x900, 1920x1080 and 2560x1440.

The **wallpaper** is different. It draws `target-2.cells`, a fixed 320x90 cell
grid, so it fills a screen exactly when `320 x cell_w` and `90 x cell_h` are
the screen's dimensions:

| screen | strike | cell |
|---|---|---|
| 1920x1080 | ter-112n | 6x12 |
| 2560x1440 | ter-116n | 8x16 |
| 3840x2160 | ter-124n | 12x24 |

At 1920x1080 nothing needs doing. At any other size the hero is drawn at its
old pixel size in the corner, and re-tuning is two commands — a font
rasterisation, seconds, no GPU and no raytrace:

    cd /opt/rice
    ./bin/machine generate                       # reads the new panel
    python3 bake/bake_atlas.py \
      --font /usr/lib/kbd/consolefonts/ter-116n.psf.gz \
      --out assets/atlas-bake.bin                # the strike `generate` chose

then log out and back in. (`bake_atlas.py` could not do this until today: the
8x16 strike is PSF1, and the baker read only PSF2.)

## The machine profile

`machines/<hostname>.conf` is keyed on hostname, and **the hostname travels
with the disk** — so a stale profile still resolves and still looks right.

In the nulllinux tree this is handled: `nulllinux-machine-sync.service` runs on
every boot, compares the recorded output and mode against the hardware, and
regenerates plus re-selects the atlas, hero and theme when they differ. An
ordinary boot costs ~210 ms and changes nothing.

**This disk runs `/opt/rice`, which has no such service**, so its profile must
be regenerated by hand as above.
